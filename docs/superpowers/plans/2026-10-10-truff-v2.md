# Truff v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans или superpowers:subagent-driven-development для выполнения плана по задачам. Способ исполнения выбирается при переходе к реализации; этот документ разрешает только планирование.

**Goal:** Нативный Markdown-редактор с цельным интерфейсом в духе Obsidian, единым Vim-управлением текстом и хранилищем, малыми затратами памяти и предсказуемой отзывчивостью.

**Architecture:** Независимое ядро владеет буферами, командами и моделью рабочего пространства; хранение и фоновые задачи находятся в отдельном крейте; retained UI отображает ограниченную проекцию состояния. Исходный Markdown, его синтаксическая структура и визуальная раскладка разделены. Все изменения текста проходят через одну транзакцию, все панели используют один реестр команд и общий механизм навигации по строкам.

**Tech Stack:** Rust; Masonry + masonry_winit, Parley и штатный Vello/wgpu; crop; Tree-sitter Markdown; pulldown-cmark для семантического извлечения; rusqlite/SQLite FTS5; notify; serde + TOML. Версии закрепляются после P0 в Cargo.lock, совместимые компоненты Masonry берутся из одного релиза.

**Spec:** [my_idea_main.md](../../my_idea_main.md), [gpt_idea.md](../../gpt_idea.md), текущие пользовательские ограничения и [AGENTS.md](../../../AGENTS.md).

**Статус:** План реализации, 10 октября 2026 года. Код приложения, прототипы и бенчмарки ещё не созданы; все численные показатели ниже являются целями и стартовыми лимитами, а не измеренными результатами. В текущем Truff_v2 есть документы и правила .agent/, но нет Cargo workspace. Архитектура другой копии Truff сюда автоматически не переносится.

## 1. Global Constraints

- GPUI исключён из проекта и его зависимостей.
- Приоритет: корректность и сохранность данных → измеренная скорость и память → поддерживаемость → количество строк.
- Ориентир 5–7 тысяч строк собственного кода мягкий; его нельзя обеспечивать минификацией, удалением проверок или ухудшением требуемых функций.
- Учитывать отдельно production Rust, тесты, бенчмарки/инструменты и общий собственный код. Зависимости, сгенерированные парсеры, документы и Markdown-fixtures не включать в собственный Rust; их размеры показывать отдельно.
- Один канонический владелец каждой ответственности; тонкие UI-обработчики; никаких циклов зависимостей, складов utils/common и инфраструктуры «на будущее».
- Файлы свыше 300–500 строк пересматривать по ответственности; разделение по смыслу, а не механически по числу строк.
- Markdown-файлы — источник истины. SQLite — удаляемый и восстанавливаемый индекс; потеря индекса не должна уничтожать заметки.
- UI-поток не читает каталог, не пишет файлы и не выполняет SQL или полный разбор документов.
- Очереди, результаты, кэши, история и временные снимки имеют пределы; dirty-буферы не вытесняются молча.
- Shell-команды выполняются через rtk; для необработанного вывода — rtk proxy.
- Реализация следует .agent/ARCHITECTURE.md, PERFORMANCE.md, CONCURRENCY.md, BENCHMARKING.md и RUST_STYLE.md.
- Предположение платформы: сначала Linux/Wayland с проверкой X11. macOS/Windows — последующее подтверждение переносимости, не заявленная поддержка без проверки.
- Предположение Vim: собственный практичный движок, а не полная совместимость с Vim/Neovim. Матрица команд в §7 фиксирует границы; расширение совместимости требует пересмотра бюджета.
- До прохождения P0 не разрабатывать весь интерфейс: сначала доказать пригодность выбранного UI и текстового стека.

## 2. Review Focus

Пять условий, которым нужны отдельные проверки в задачах:

1. Кириллица, emoji, combining marks, CRLF и IME: курсор и правки не повреждают UTF-8 и не разрезают графемы — T02, T05, T09.
2. Внешнее изменение dirty-файла и ошибка сохранения: не перезаписывать чужую версию и не показывать ложное «сохранено» — T04.
3. Поздний ответ парсера/поиска после правки, закрытия файла или смены vault: не менять актуальное состояние — T03, T06, T10.
4. Очень длинная строка, большая заметка и широкая папка: ограничивать работу, память и UI-объекты без зависания — T01, T07, T08, T09.
5. Повторные ссылки, одинаковые имена, циклы графа и прерывание переименования: сохранять неоднозначность и восстановимость — T10, T11, T15.

## 4. Какие идеи из gpt_idea.md становятся архитектурой

| Идея | Решение Truff v2 | Каноническое место | Проверка |
| --- | --- | --- | --- |
| 1. Дизайн-токены | Одна Theme с цветами, оттенками, размерами, шрифтами и версиями. Светлая/тёмная палитры — данные | ui/theme.rs | Смена темы обновляет все панели; значения не размножаются в виджетах |
| 2. Live Preview | Buffer → SyntaxSnapshot → DisplayMap → видимые ParagraphLayout. Motions используют исходник | core/markdown/, ui/editor/ | Редактирование скрытого маркера, hit-test и undo сохраняют исходный Markdown |
| 3. Виртуализированное дерево | RowModel и один VirtualRows для vault, буферов, TOC, backlinks, picker и будущего дерева графа | core/navigation/, ui/rows.rs | Число строк/виджетов зависит от viewport, не от числа файлов |
| 4. Retained UI и типизированные handles | Штатные WidgetId/WidgetTag<W>/WidgetMut Masonry; активная панель получает Action | ui/driver.rs, ui/shell.rs | Смена фокуса не пересоздаёт редактор и не дублирует командный код |
| 5. Отдельный resolver | Обнаружение ссылки, разрешение Target и команда открытия разделены. Один resolver обслуживает picker, backlinks и rename | core/markdown/links.rs, store/index/resolve.rs | Одинаковые имена дают Ambiguous, повторные вхождения остаются отдельными |
| 6. Сессия и буферы | BufferId отдельно от ViewId; курсор/scroll принадлежат виду, текст/undo — буферу | core/workspace/, store/session.rs | Закрытие вкладки не удаляет dirty-буфер; два вида видят одну правку |
| 7. Частичное обновление | Разделить text/syntax/layout/theme invalidation. Движение курсора обновляет overlay, не раскладку абзацев | ui/editor/, ui/driver.rs | Счётчики reparse/shape/layout не растут от одного движения курсора |
| 8. Независимое событийное ядро | Action → Workspace → Effects; StoreEvent возвращается с поколением. UI только адаптирует события | core/workspace/, store/worker.rs | Основные сценарии воспроизводятся без запуска окна |
| Будущее: граф | Один индекс ссылок и GraphSnapshot; режимы меняют представление, а не происхождение связей | core/graph.rs, ui/graph.rs | Циклы и повторные ссылки не портят модель |
| Будущее: история | Текстовые undo-транзакции отдельно от durable recovery файловых операций | core/text/, store/operations.rs | Undo и crash recovery проверяются разными сценариями |

Важное уточнение идеи 7: локальный request_paint не доказывает частичную растеризацию framebuffer. В первом релизе сохраняются раскладки и уменьшается работа приложения; поведение штатного Vello измеряется отдельно. Собственный damage-tracker, хеширование всех draw-команд и CPU-рендерер не разрабатываются без измеренного основания.

Переносить принципы, не исходные модули Aquilum. Не наследовать его числовые пределы 160/40 как универсальные; запас виртуализации определяется размерами viewport.

## 5. Выбор стека и проверка до основной реализации

### 5.1. UI

Основной выбор — **Masonry напрямую**, со штатным masonry_winit. Причина: retained widgets, общий фокус и ввод, типизированные теги и Parley согласуются с архитектурой из gpt_idea.md. Для редактора и виртуального списка нужны собственные виджеты; оболочка собирается из готовых компонентов.

Masonry использует Parley и Vello/wgpu; это подтверждённая структура зависимостей, а не доказательство малого RSS. Начальный совместимый кандидат — семейство Masonry 0.4.0; точные версии и доступные API подтверждаются компиляцией T01. [Документация Masonry](https://docs.rs/masonry/0.4.0/masonry/), [архитектура Linebender](https://raw.githubusercontent.com/linebender/xilem/main/ARCHITECTURE.md).

| Вариант | Польза | Цена и решение |
| --- | --- | --- |
| Masonry + штатный backend | Близок к нужной retained-архитектуре; готовый текстовый стек | Основной кандидат. Память GPU backend и объём интеграции — обязательный P0 |
| egui/eframe + glow | Простая оболочка, готовая оконная интеграция | Резервный сравнительный прототип, только если Masonry не проходит P0; потребуются явные сохранённые layout-кэши |
| Собственный winit + renderer/widgets | Максимальный контроль | Не помещается разумно в бюджет первой версии; не выбирать без конкретного непреодолимого ограничения |

Резерв не является вторым production frontend. При отказе Masonry сохранить независимые core/store, заменить ui и обновить этот план до T02. Не поддерживать два renderer одновременно. Буквально копировать CPU-интеграцию Aquilum не требуется.

### 5.2. Текст и Markdown

- **crop::Rope** — основной текст. Использовать байтовые диапазоны, chunks и дешёвые снимки; подтвердить свойства снимков и реальные расходы в P0. String разрешён для небольших UI-полей и bounded временного входа семантического parser, но не как вторая постоянная копия буфера. [API crop](https://docs.rs/crop/latest/crop/struct.Rope.html).
- **Tree-sitter** — инкрементальная структура для подсветки, Flash и text objects; кормить через callback по chunks Rope. Изменять старое дерево через InputEdit перед parse; координаты Point.column — байты, не экранные колонки. [Инкрементальный разбор](https://tree-sitter.github.io/tree-sitter/using-parsers/3-advanced-parsing.html).
- Markdown Tree-sitter имеет block/inline grammars; диапазоны inline задаются после block parse. Грамматика прямо предупреждает о неточностях: не использовать её одну как доказательство корректности изменения ссылок на диске. [README грамматики](https://github.com/tree-sitter-grammars/tree-sitter-markdown).
- **pulldown-cmark** — каноническое семантическое извлечение headings и Markdown-links в фоне; небольшой единый extractor wiki/block расширений работает только вне исключённых code-диапазонов. Результат DocFacts используют индекс, TOC, resolver и проверка rename.
- Два parser выполняют разные задачи. Не заводить по parser для каждой панели. Семантический проход происходит при индексации/сохранении и debounce активного документа, а не при каждой отрисовке.
- Unicode-сегментация — unicode-segmentation; предложений сначала достаточно пунктуационных правил для русского/английского, не обещать лингвистическую полноту.
- **SQLite FTS5** — полнотекстовый поиск на диске; bounded page cache. Индекс заголовков/ссылок отдельными таблицами, без загрузки всех текстов в RAM.
- notify сообщает изменения, worker объединяет их и сверяет с диском. Событие watcher не считается доказательством точного состояния файлов.

### 6.1. Единая текстовая транзакция

Transaction содержит непересекающиеся byte-range edits, позицию/выделение инициирующего вида и UndoGroup. До изменения проверить все диапазоны, UTF-8, итоговый размер и разрешённость операции. Ошибка оставляет исходный текст и историю целыми.

Применить изменения от больших offsets к меньшим. ChangeSet содержит изменения для rebasing курсоров/anchors, парсера и layout invalidation. Undo/redo, paste, macros, оформление, создание ссылки и mouse actions идут через этот же путь. Revision — монотонное поколение, увеличивается также при undo; отдельный savepoint определяет dirty.

Vim работает в source coordinates. j/k — логические строки; gj/gk — visual lines через DisplayMap. h/l и удаления движутся по графемам; Tree-sitter offsets остаются байтами. Неполный Markdown не запрещает обычное редактирование.

### 6.2. Фоновые поколения и backpressure

SnapshotKey = (VaultEpoch, BufferId, Revision). Поиск дополнительно имеет QueryGeneration. Директории и индекс — собственные поколения. Workspace проверяет весь ключ до применения ответа; совпадения только пути или только revision недостаточно.

Сначала два рабочих потока: syntax; store/index/I/O. notify может создавать собственные потоки — это учитывать в process metrics. Снимки неизменяемые; общего Arc<Mutex<AppState>> нет.

- replaceable parse/search: максимум один ожидающий job на активный ключ, старый результат отбрасывается;
- durable load/save/rename: bounded очередь, try_submit; при переполнении команда остаётся явно ожидающей либо не принимается с понятным сообщением;
- accepted durable jobs не теряются и не отменяются заменой поискового запроса;
- UI только try_recv; worker будит штатный event loop;
- индексатор обрабатывает один файл/пакет и снова проверяет интерактивную очередь; не ставит весь vault перед save/search;
- watcher overflow создаёт один reconcile-запрос, а не очередь из тысяч событий;
- если приоритетам мешает измеренно долгий DB/job, добавить отдельный I/O worker; решение и его память фиксировать измерением;
- shutdown: остановить новые задачи, завершить уже принятые durable операции, сохранить сессию, закрыть DB и join workers.

## 7. Один Vim-ввод и один реестр команд

CommandSpec содержит id, описание, группы which-key и допустимые InputContext. Keymap из TOML компилируется при загрузке; lookup и hints используют одну структуру prefixes. Одинаковая команда доступна через клавиши, picker и UI-кнопку.

| Область | Команды первой версии |
| --- | --- |
| Текстовые режимы | Normal, Insert, Visual character/line; Esc; i/a/I/A/o/O |
| Motions | h/j/k/l, w/b/e, 0/^/$, gg/G, f/F/t/T, ;/,, {/}, counts; gj/gk |
| Операторы | d/c/y с motion/text object; dd/cc/yy, x, p/P, >/< |
| Text objects | iw/aw, предложения/абзацы, пары кавычек/скобок; Markdown link, heading section, code block |
| История | u, Ctrl-r, .; unnamed и named registers; q{reg}/@{reg} с пределом команд |
| Поиск/буферы | /, ?, n/N; :w, :q, :wq, :e, :b, :bn/:bp/:bd |
| Панели | Ctrl-w h/j/k/l; j/k, gg/G, /, Enter, h/l для RowModel |
| Файлы | Явные Action CreateFile/CreateFolder/Rename/Move/Trash; имена вводятся в picker |
| Заметки | FollowLink, LinkSelection, OpenBacklinks, CreateNote, OpenTargetHeading |
| Оформление | SetTextColor, SetHighlightColor, WrapCallout, SetPaneAccent |
| Flash | JumpWord, SelectSentence, SelectParagraph, SelectSyntaxObject |

Панели разделяют parser counts/prefixes и RowModel-навигацию, но не притворяются текстовым буфером: d в vault перемещает выбранные файлы в recovery/trash, d в редакторе формирует текстовую транзакцию. Действие разрешает InputContext. Не копировать Vim state machine в каждой панели.

Which-key появляется через 300 мс после незавершённого prefix, немедленно по явной команде; показывает только доступные продолжения. Complete binding не выполняется до развязки конфликтующего prefix: keymap validation требует явного правила для такого конфликта.

Flash получает только видимые targets + небольшой запас: стабильная сортировка по source position, метки из домашнего ряда, далее двухбуквенные. Метки обозначают target или начало/конец диапазона; UI рисует границы. Operator-pending + Flash → обычный Range → Transaction. Предложения/слова получаются сегментацией, Markdown-объекты — Tree-sitter; parser предложения не требуется.

Макросы записывают канонические команды и текстовые commits, не IME-preedit и не OS key events. Начальные лимиты: 1 000 commands в макросе, 10 000 исполненных команд за запуск, без рекурсивного replay.

## 8. Live Preview, интерфейс и цвета

### 8.1. Три представления одного источника

1. **Buffer** содержит только исходный Markdown.
2. **Syntax/DocFacts** описывают ranges и смысл без UI-объектов.
3. **DisplayMap + ParagraphLayout** отображают видимую область, hidden markers и hit-testing.

Один EditorWidget обслуживает Source и Live Preview; различается проекция, не текстовый движок. Начальная поддержка: headings, emphasis/strong, lists/task lists, links/wiki links, blockquotes/callouts, fenced code, простой table block. Сложная таблица в первой версии остаётся оформленным исходником; её данные никогда не теряются.

Конструкция под caret или затронутая выделением раскрывает маркеры. Скрытый диапазон имеет явную affinity к краю; редактирование на этом краю сначала раскрывает исходник. Переключение режима сохраняет source selection и верхний source anchor.

HeightIndex хранит компактные высоты блоков, а не их тексты/layout. Layout строится только для viewport ± один экран. Неизвестные высоты оцениваются; уточнение сохраняет верхний anchor, не вызывает прыжка к центру. Ширина/font changes создают LayoutEpoch и лениво обновляют видимые блоки. Изменение цвета не запускает Markdown parse.

Не обещать O(1) для всех edits: изменение fence/list может расширить изменённую синтаксическую область, а initial parse остаётся зависимым от размера документа. Длинный один блок делить на визуальные строки/страницы layout или перейти в source fallback; нельзя shape всего multi-megabyte paragraph на UI.

### 8.2. Внешний вид

Одна оболочка: узкая боковая полоса действий, дерево vault слева, буферы/вкладки сверху, редактор по центру, опциональная панель backlinks/TOC справа, statusline снизу. Панели стыкуются ровно; плавающие служебные «окна» не являются базовым layout.

Theme хранит bg/surface/raised/text/muted/border/accent/selection/caret и последовательную шкалу отступов 4/8/12/16/24. Начальные размеры: разделитель 1 logical px, row 28 px, UI font 14 px, editor 16 px; настройки масштаба меняют их через tokens. Два состояния панели: активная/неактивная; фокус обозначается также рамкой/индикатором, не только цветом.

Светлая и тёмная темы, согласованные hover/selected оттенки, хорошо читаемые метки Flash/which-key. Проверить HiDPI 100/150/200%, кириллический font fallback и управление без мыши. Иконки — небольшой общий набор SVG/path, без загрузки большого icon font.

### 8.3. Цвет — обязательная функция первой версии

Цветовые команды работают из Visual, picker и кнопок через одну Transaction:

- цвет текста: ограниченное inline-расширение `<span style="color:#RRGGBB">…</span>`;
- выделение фрагмента: `<mark style="background-color:#RRGGBB">…</mark>`;
- цветной блок: Obsidian-подобный callout `> [!note]` с mapping типа на Theme;
- оттенок целой панели: session/theme setting, без изменения Markdown.

Цвет сохраняется в самом Markdown; конкретный renderer может показывать HTML иначе — полную совместимость оформления с другими приложениями не заявлять. Recognizer поддерживает только эти формы и цвета; не превращать его в CSS/HTML engine.

Wrapper не должен пересекать code fence или разрывать link delimiter. Выделение нескольких блоков преобразуется в callout либо несколько допустимых inline spans; команда заранее показывает выбранный вариант. Повторное изменение цвета обновляет существующий wrapper, не вкладывает бесконечные spans. RemoveColor снимает только известные собственные оболочки. Undo возвращает точный исходник.

Изображения/attachments в первой версии открываются по ссылке; thumbnails и embeds добавлять лишь при отдельном бюджете декодирования. Они не требуются для перечисленных пользовательских сценариев.

## 9. Хранилище, ссылки и сохранность данных

### 9.1. Буферы и сессия

BufferId уникален в сессии, не равен пути. Запись registry имеет состояния Unloaded/Clean/Dirty/Conflict; unloaded buffer сохраняет metadata, но не Rope/дерево/layout. Открытие нового вида использует существующий BufferId.

Невидимые clean-буферы можно unload по бюджету; undo clean-буфера теряется только по документированной политике и с обозначением в списке. Dirty-буфер сохраняется в RAM либо явно предлагается сохранить/закрыть; автоматическое вытеснение запрещено.

session.toml: vault, buffer paths, views, focus, source caret/scroll anchors, размеры/цвета панелей, раскрытые папки и jump history. Не сериализовать текстовые layout/Tree-sitter trees. Восстановить metadata сразу, активный текст первым, остальные лениво. Missing paths остаются понятными закрываемыми записями.

### 9.2. Запись и recovery

SaveJob несёт SnapshotKey и базовый fingerprint. Перед записью worker проверяет актуальное содержимое диска; затем temp в том же каталоге → flush/sync → atomic rename → directory sync на поддерживаемом Linux FS. Метаданные исходного файла сохраняются по определённой политике; создание новой заметки не перезаписывает существующую.

SaveAck относится к сохранённой revision. Если пользователь уже сделал следующую правку, буфер остаётся dirty. Hash/fingerprint — защита от незамеченного конфликта, но между проверкой и rename остаётся гонка с несотрудничающим внешним writer; абсолютную cross-process atomic compare-and-swap не обещать. Для собственной второй instance использовать advisory vault lock.

Внешняя правка clean-буфера → reload с rebasing/проверкой anchors; dirty-буфера → Conflict с выбором reload/save-as/явного overwrite. Watcher-событие собственной записи подавляется по fingerprint, не произвольным sleep.

Recovery — отдельные атомарные снимки dirty-документов после idle 750 мс, с base fingerprint и generation; один актуальный плюс предыдущий валидный снимок. Ограничение 256 MiB на vault recovery; при заполнении сообщить о невозможности дальнейшей защиты и предложить сохранить, не удалять единственную несохранённую копию. RecoveryAck определяет последнее гарантированно записанное состояние; последние правки до ack могут потеряться при аварии. :w имеет более сильное подтверждение FileSaved.

### 9.3. Индекс и resolver

Минимальная схема с PRIMARY KEY/индексами и version в schema.sql:

| Таблица | Содержание |
| --- | --- |
| files | FileId, relative_path UNIQUE, title, fingerprint, index_generation |
| headings | (file_id, ordinal), level, text, anchor, byte_start/end |
| blocks | (file_id, block_anchor), byte_start/end |
| links | (source_file_id, occurrence_ordinal), source range, raw Target, nullable resolved FileId/anchor |
| notes_fts | title/body, unicode61, одна дисковая FTS5 content-копия для поиска |
| operation_log | recovery manifest для незавершённых файловых операций |

Не заводить вторую SQLite body-таблицу поверх обычной FTS content-копии. При измеренно большом дисковом индексе отдельно рассмотреть contentless variant; усложнение обновлений/сниппетов не вводить заранее. Сам индекс никогда не становится авторитетным текстом.

Target: Note { path_or_name, heading_or_block, alias } или ExternalUrl. Resolution: Found, Missing, Ambiguous, StaleIndex. Exact relative path имеет приоритет; basename используется лишь при единственном совпадении. Сравнение путей учитывает platform case rules; не применять lowercase к файловым путям Linux.

Поддержать [[Note]], [[dir/Note#Heading|Alias]], [[Note#^block-id]], Markdown [label](relative.md#heading); не трактовать fenced/inline code и escaped delimiters как ссылки. Каждый occurrence хранится отдельно, в том числе две ссылки на одну заметку. Неявный выбор при дубликате заголовка запрещён: picker показывает контекст; persisted target можно закрепить block-id.

Backlinks — обратная SQL-выборка occurrences с pagination. Dirty-активный документ имеет маленький overlay DocFacts, который замещает его дисковую версию, а не удваивает backlinks. SearchPage ≤100 строк; snippets читаются только для текущей страницы.

### 9.4. Файлы и папки

Один FileOpPlan для Create/Rename/Move/Trash. Сначала validate paths/locks/conflicts; затем ограниченный manifest, staging/backups, apply и recovery. Пути остаются внутри vault; внутренние symlinks не обходятся рекурсивно, writes через symlink запрещены в первом релизе.

При rename файла/папки resolver определяет затронутые occurrences; проверить исходники заново по DocFacts и fingerprints. Dirty affected buffer либо включается в явно подтверждённый save-plan, либо операция останавливается с перечнем препятствий. Ссылки внутри code/неоднозначные targets не переписываются.

Перед применением пользователь видит список файлов и число ссылок; это продуктовый preview опасной пакетной операции, а не вопрос о каждой обычной клавише. Cross-file атомарность файловой системы не обещать: manifest должен позволять завершить либо восстановить операцию после любого шага.

Trash перемещает объект в .truff/trash с исходным путём; постоянное удаление — отдельное явное действие вне первой версии. Не объединять файловый undo с текстовым u: восстановление операций доступно через отдельную историю.

## 10. Память, задержки и масштаб

### 10.1. Стартовые лимиты

Все MiB — 2^20 bytes. Пользователь может менять лимиты в TOML; их проверка выполняется один раз на границе config.

| Ресурс | Начальное значение | При превышении |
| --- | --- | --- |
| Редактируемая заметка | 16 MiB | Сообщение и отдельное открытие внешним инструментом; не грузить молча |
| Rich parse/Live Preview | 2 MiB | Source mode с ограниченной подсветкой/Flash, причина видна |
| Строка/абзац для полного shaping | 64 KiB | Chunked source layout; ограничить сложный rich preview |
| Загруженные clean texts | 16 MiB суммарно | Unload наименее используемых невидимых clean |
| Dirty texts | 32 MiB soft, 64 MiB admission cap | Предложить сохранение/закрытие; не терять уже принятые edits |
| Undo + регистры | 8 MiB на буфер, 24 MiB суммарно | Удалять старые undo groups с явной границей истории |
| UI layouts | 12 MiB, 512 entries максимум | LRU eviction вне viewport |
| Tree-sitter | Активный + максимум 1 соседний документ | Удалить невидимые деревья; measured heap входит в общий бюджет |
| SQLite page cache | 8 MiB на connection; сначала одна | PRAGMA и memory metrics; дополнительные connections учитываются отдельно |
| Background jobs | 32 durable slots; replaceable jobs по ключу | Backpressure; payloads ≤32 MiB суммарно |
| Search/TOC/backlinks | Page 100; query input ≤256 chars | Pagination/validation |
| Сессия | 256 buffer records, 32 views, 256 jump entries | Явное ограничение новых записей |
| Virtual rows | Видимые + по 1 viewport с каждой стороны | Без создания полного дерева widgets |
| Recovery | 256 MiB на диске на vault | Ошибка защиты + действие сохранения |

Это не обещание жёсткой верхней границы RSS: драйвер, allocator, Parley/fonts и grammar имеют собственные расходы. Ограничивать приложение через admission/eviction и проверять retained/peak memory, а не суммировать одну таблицу.

Rope snapshots дешёвы только пока общие chunks живы; undo и очередь могут удерживать удалённые мегабайты. Считать retained memory и лимитировать snapshots/replay deltas. Переполнение истории не делает edit частичным. max_file_bytes проверяется также для paste, link/color wrappers, macro и redo.

### 10.2. Цели всего приложения

Первый benchmark-host: пользовательская Linux-машина; зафиксировать CPU/RAM/GPU/driver/OS, экран 1920×1080, масштаб 100%, release build. Числа первоначальные; P0 подтверждает или обосновывает пересмотр. Нельзя молча называть их достигнутыми.

| Сценарий | Цель |
| --- | --- |
| Пустое окно после стабилизации | RSS ≤100 MiB, желательная цель ≤60 MiB |
| Vault 10k × 4 KiB, 1 активный файл 64 KiB, 10 buffer records | RSS ≤160 MiB; overhead сверх пустого окна ≤60 MiB |
| Vault 100k × 4 KiB, активен 1 файл | RSS ≤240 MiB; file metadata/paging не требует resident body texts |
| Ввод/source motion в заметке ≤1 MiB | Core edit/motion p95 ≤2 мс; input-to-present p95 ≤25 мс |
| Scroll при тёплом viewport | Frame p95 ≤16.7 мс на benchmark-host |
| Изменение обычного абзаца в Live Preview | Visible layout ready p95 ≤50 мс; ввод доступен сразу |
| Открытие заметки ≤1 MiB на тёплом FS | Первая доступная source-область p95 ≤100 мс |
| Поиск/picker при готовом индексе 10k | Ответ первой страницы p95 ≤100 мс |
| Flash в видимой области | Метки p95 ≤30 мс; не сканировать весь vault/document |
| Тёплый запуск с готовым индексом | Source editing доступен ≤700 мс |
| Простой 30 секунд без ввода | CPU ≤1% одного ядра в среднем; нет постоянного frame loop |

Штатный GPU framebuffer может растеризоваться целиком. Считать отдельно время приложения, framework/render и presentation. CPU heap, RSS/PSS и VRAM — разные показатели; memory savings core не подменяют стоимость окна.

### 10.3. Метод измерений

В T01/T13 создать воспроизводимый harness, генерирующий данные с seed=20261010:

- small: 1k × 4 KiB; normal: 10k × 4 KiB; stress: 100k × 4 KiB;
- notes: 64 KiB, 1 MiB, 16 MiB; одна строка 1 MiB; много headings/links;
- directory: 10k siblings и глубина 100; Cyrillic/emoji/CRLF fixtures;
- 500 normal edits, delete/paste мегабайта, undo/redo, 1k macro steps;
- 50 переключений видов одного буфера; закрытие/открытие; rename с 100 references;
- edit/search одновременно с initial indexing; late responses и watcher storm.

Для warm latency 5 отдельных запусков после warmup, ≥200 событий на сценарий; p50/p95/p99 и peak/steady memory. Настоящий cold FS нельзя объявить из удаления app-cache: отдельно указать OS page-cache условия. Startup — начало процесса → реально доступный ввод, не только создание окна.

GUI-harness воспроизводит события/состояние и собирает timestamps; фактический input-to-present требует backend presentation instrumentation и реальной Wayland-сессии. Headless результаты показывать отдельно. `/usr/bin/time -v` даёт process peak, `/proc/<pid>/smaps_rollup` — текущие RSS/PSS. Heap profiler запускать отдельно, его overhead не включать в основное timing-сравнение.

Результат: `docs/perf/<stage>/metadata.toml`, `samples.csv`, `summary.md` и воспроизводимые команды. Отдельно размеры бинарника, Cargo dependency tree и число потоков. Перед/после — эквивалентные workload, настройки и семантика. Замедление >5% вне шума требует расследования; правило .agent/BENCHMARKING.md о заметных малых регрессиях также сохраняется.


Harness contract фиксируется в T01: corpus.rs использует только std и принимает --out, --notes, --bytes, --seed; measure.sh принимает --vault, --scenario, --runs, --out. Внутренний GUI scenario runner включается feature perf, выполняет команды через тот же Workspace и не показывается в обычном интерфейсе. В частности:

~~~bash
rtk proxy rustc --edition=2024 -O tools/perf/corpus.rs -o /tmp/truff-corpus
rtk proxy /tmp/truff-corpus --out /tmp/truff-normal --notes 10000 --bytes 4096 --seed 20261010
rtk cargo build --locked --release -p truff-ui --features perf
rtk proxy tools/perf/measure.sh --vault /tmp/truff-normal --scenario edit-scroll --runs 5 --out docs/perf/p7
~~~

measure.sh получает пути без shell-eval; перед созданием corpus отказывается перезаписывать непустую директорию. Набор сценариев в scenarios.toml включает startup, edit-scroll, flash, search-during-index и rename-recovery. Метрики reported Core/GUI/Presentation имеют собственные границы, а не общий суммируемый nested timer.

## 11. Порядок реализации и конкретные задачи

## 12. Бюджет кода и предотвращение повторов

Оценка v1 — P0–P7. Это бюджет ответственности, не лимит на файл и не обещание точного количества строк.

| Область | Собственные production строки |
| --- | ---: |
| Text, transactions, history | 700 |
| Vim parser/motions/execute | 950 |
| Markdown syntax/facts/links/style | 700 |
| Workspace/navigation/commands/config | 750 |
| Store/files/recovery/workers/session/index/operations | 1 200 |
| UI shell/rows/overlays/theme/driver | 650 |
| Editor display/layout/paint/input | 850 |
| **Production v1** | **5 800** |
| Tests + perf tools | 900–1 200 |
| **Весь собственный код v1** | **6 700–7 000** |

Бюджет амбициозный для GUI + Vim + recovery; T01/T13 могут показать необходимость его увеличения. Сначала убрать вторые реализации/лишние features и переиспользовать зрелые primitives; корректность и требуемое поведение не удалять ради числа.

P8–P10 ориентировочно добавят 1 200–2 000 production/test строк до вычета переиспользования. Поэтому обещать все будущие функции в суммарных 7k без прототипа нельзя. На каждом этапе показывать net growth и общий размер; ориентир пользователя сохраняется как повод упрощать архитектуру, не как повод скрывать код тестов.

Канонические механизмы, которые сокращают проект:

1. Один apply для всех текстовых edits.
2. Один Vim parser и один registry/prefix map для клавиш, picker, which-key и кнопок.
3. Один RowModel/VirtualRows для списков и деревьев.
4. Один MarkdownFacts extractor для headings/links/index/TOC/rename validation.
5. Один resolver для FollowLink, LinkSelection, backlinks и suggestions.
6. Один EditorWidget и DisplayMap для Source/Live Preview.
7. Одна Theme для цветов панели, текста и callouts.
8. Один session model; один FileOpPlan для recoverable файловых операций.

Не строить plugin SDK, dynamic module loading, arbitrary HTML/CSS renderer, LSP, полносовместимый Ex/Vimscript, sync/cloud, universal event bus или отдельные managers без текущего владельца. Это не исключает расширение позже, но оно не требуется данными документами.

Бюджет превышен — сначала удалить дубликаты, сократить public API, выяснить, не пишет ли UI доменную логику, и заменить самодельный зрелый primitive библиотекой. Не сжимать нечитаемые выражения и не дробить cohesive state machine ради счётчика.

## 13. Проверки и завершение этапов

После создания workspace применяются команды:

~~~bash
rtk cargo fmt --all -- --check
rtk cargo check --locked --workspace --all-targets
rtk cargo test --locked --workspace
rtk cargo clippy --locked --workspace --all-targets --all-features -- -D warnings
rtk cargo build --locked --release -p truff-ui
~~~

Тесты используют временные vault без пользовательских данных. Property-style проверки нужны для edit ranges, undo и source/visual mapping; fault injection — для save/recovery/file operations; table-driven fixtures — для Vim и ссылок. Не дублировать тестами каждую Theme-константу.

Документ этого плана проверить отдельно: все R01–R17 покрыты задачами; ссылки/пути согласованы; есть владельцы, bounded policies, assertions и commands; нет TBD/TODO вместо решений. Проверка Markdown не является проверкой Rust приложения.

При завершении каждой задачи:

- [ ] Сверить фактический API с Interfaces/Produces и обновить план при необходимом изменении.
- [ ] Выполнить относящиеся проверки, прочитать ошибки/exit code.
- [ ] Просмотреть diff на duplicate logic, hot-path clones, неограниченные collections и ошибки сохранности.
- [ ] Показать, что измерено, что является допущением, и изменение общего бюджета кода.
- [ ] Сохранить маленький commit только файлов задачи; существующие пользовательские документы не захватывать автоматически.

Выполнение будущего этапа начинается с собственного короткого уточнения scope, если появились новые пользовательские требования. Этап считается завершённым по работающему сценарию и измерениям, а не по наличию файлов или количеству строк.

## 14. Риски и решения при провале

| Риск | Ранний сигнал | Действие |
| --- | --- | --- |
| GUI/backend расходует слишком много памяти | P0 empty RSS выше цели | Проверить allocator/driver/fonts; эквивалентный резервный probe; выбрать один stack до расширения UI |
| Layout/IME/custom EditorWidget разрастается | P0 glue сложен, hit-test некорректен | Использовать штатные Parley primitives, сократить поддержку rich конструкций до корректного source fallback |
| Tree-sitter и Markdown semantics расходятся | Fixtures code/wiki/heading не проходят | DocFacts — источник индексных фактов; TS — syntax hints; unsafe refactor блокируется |
| Snapshot/undo удерживает удалённые мегабайты | Peak/retained растут после delete/undo | Ограничить lifetime/очередь и history; не считать cheap clone нулевой памятью |
| Индексация задерживает save/search | Latency во время initial scan | Yield между файлами/DB batches; отдельный worker лишь по измерению |
| Multi-file rename становится большим subsystem | T11 превышает объём/сложность | Сохранять preview/recovery; сократить поддерживаемые операции первой версии явно, не делать небезопасный rewrite |
| n-граммы плохо находят русские формы | Отдельный набор recall/precision | Пересмотреть ranking/normalization; morphology после независимого сравнения |
| Все желания превышают 7k | Отчёт после каждого этапа | Переиспользование, обоснованный рост и явная оценка; не скрывать тесты и не жертвовать корректностью |

Следующее действие при реализации — T01. На текущем шаге результатом является этот план; реализация приложения и доказательство численных целей остаются будущей работой.

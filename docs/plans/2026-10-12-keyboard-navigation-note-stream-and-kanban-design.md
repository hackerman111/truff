# Vim-управление, организация заметок, лента и kanban

Дата: 2026-10-12. Статус: концепция согласована пользователем; реализация ещё не начата.
Дополнение пользователя: быстрый поиск является обязательным требованием.

## Цель и принятые решения

Основные сценарии Truff выполняются без мыши: редактирование любого текста,
выбор заметки, папки или хранилища, поиск, переходы по ссылкам, чтение старых
записей и управление kanban. Which-key показывает доступные команды текущего
контекста. Все новые представления используют действующие тему и геометрию.

Пользователь подтвердил модель ленты: отдельные Markdown-файлы показываются
вместе; новая запись сохраняется отдельным файлом. Лента должна помогать
возвращаться к старым записям, а не только показывать последние.

Остальные конкретные клавиши и форматы ниже — предлагаемые решения. «Неявный
поиск» трактуется как поиск по неполному названию, пути, заголовку и содержимому
без необходимости знать точное имя файла. Семантический поиск с моделями и
лингвистическая нормализация не подразумеваются.

## Фактическое состояние проекта

- В workspace существуют `truff-core`, `truff-store`, `truff-ui`.
- Нативное приложение использует egui/eframe: `ui/native/events.rs`, `sidebar.rs`,
  `backlinks.rs`. Указание Masonry в README и старом плане устарело. Смена UI-стека
  не входит в эту работу; ограничение без GPUI сохраняется.
- Vim уже поддерживает Normal/Insert/Visual, counts, операторы, регистры,
  макросы, поиск, text objects и source-coordinate motions.
- `CommandRegistry`, `CompiledKeymap`, `VimState` и `RowModel` существуют;
  новую реализацию этих механизмов создавать не требуется.
- `Shell::feed_key` отдельно обрабатывает панели и `Ctrl-w`; дефолтный keymap
  используется преимущественно для подсказок. Обработка `j/k/Enter` backlinks
  в `native/events.rs` обходит `RowModel`; `backlink_selection` дублирует выбор.
- `MarkdownFacts` извлекает headings/links/blocks. SQLite имеет headings,
  links и FTS5; поиск в индексе существует, но единой панели поиска нет.
- Дерево строится из Markdown-путей, поэтому пустые папки требуют отдельного
  перечисления. Файловые операции уже имеют `FileOpPlan` и recovery.
- Flash размечает видимые source ranges. Режима link-follow в нём пока нет.
- В рабочем дереве до этой задачи изменены текстовое ядро, Vim editing/repeat,
  отрисовка абзацев и тесты. Их изменения сохраняются и учитываются при интеграции.

## Выбор подхода

1. **Расширить существующее ядро — рекомендуется.** Один parser, реестр команд,
   путь транзакций и модель строк обслуживают все представления. Требуются
   исправления маршрутизации и новые предметные модели, но текущие ownership
   и recovery сохраняются.
2. Встроить Neovim: больше совместимости с Vim, но отдельный процесс, RPC,
   синхронизация буфера/undo/IME и новые зависимости. Это отдельная архитектурная
   работа, оправданная требованием совместимости с плагинами Neovim.
3. Добавить хоткеи отдельно каждому виджету: меньше начальной интеграции,
   но сохраняется дублирование фокуса, motions и подсказок. Не выбран.

## 1. Единое управление и текстовые поля

Реестр команд — общий источник для bindings, which-key, палитры и кнопок.
VimParser остаётся владельцем counts, operators, registers и text objects.
Keymap маршрутизирует пользовательские привязки и команды приложения, сохраняя
ожидающие Vim-префиксы. Команды приложения не перехватывают текст Insert,
поисковый запрос, аргументы `f/t`, регистры и имена макросов.

У фокуса есть типизированная цель: редактор, строки конкретной панели,
редактируемое поле, лента или доска. Enter активирует типизированную цель строки
(путь, heading, backlink, vault); строковые payload не служат протоколом команд.
Выбор и раскрытие хранятся у модели, а не дублируются в NativeApp/Application.
Смена фокуса отменяет незавершённую команду и Flash, завершает Insert undo-group.

Каждое текстовое поле — поиск, создание/rename, заголовок карточки, путь vault —
редактируется через существующие Buffer/View/VimState и input adapter.
Поле начинает с Insert для быстрого ввода; Esc переключает в Normal.
Следующий Esc передаёт отмену владельцу поля. Enter подтверждает однострочное
поле; для многострочного текста действует редактор заметки. Paste/IME являются
атомарными транзакциями. Ограничение длины проверяется до правки.

Обязательная матрица клавиш:

| Контекст | Команды |
| --- | --- |
| Любой текст | `h/j/k/l`, `w/b/e`, `W/B/E`, `0/^/$`, `gg/G`, counts; `f/F/t/T`, `;/,`; `{/}` |
| Правки текста | `i/a/I/A/o/O`, `v/V`, `d/c/y` с motion/object, `x`, `D/C/Y`, `p/P`, `u`, `Ctrl-r`, `.`, registers, macros |
| Поиск в тексте | `/`, `?`, `n/N`; `?` сохраняет значение обратного поиска |
| Строки | counts + `j/k`, `gg/G`, `Ctrl-d/u`, `/`, `h/l` для иерархии, Enter для открытия |
| Панели | `Ctrl-w h/l/w`; `Ctrl-w j/k` учитывает расположение доступных областей |
| Подсказки | `<Space>?`, `:help`; доступные префиксы показываются из реальных bindings |
| Буферы | `<Space>bb` выбор, `<Space>bn/bp` следующий/предыдущий |

Недостающие команды матрицы добавляются в core/parser/motion/execute.
Ctrl-d/u в редакторе перемещают по фактической половине viewport; renderer
сообщает размеры, core сохраняет курсор в исходных координатах.
В панели эти команды используют количество видимых строк.

Это определённая матрица Vim-управления, а не обещание совместимости с каждым
Ex-command, плагином или настройкой Vim. Для VisualBlock и полного Ex-языка
потребуется отдельное решение о расширении требований.

## 2. Одна панель: дерево, поиск, смешанный режим, выбор хранилища

Общий picker имеет одинаковую рамку, строку запроса, список, breadcrumb,
индикатор режима и подсказки клавиш. Данные и действия различаются по типу
picker: заметки/папки, vault, буферы, headings, команды или ссылки.

Для заметок предлагаются три режима; переключение Tab, обратное Shift-Tab:

- **Дерево:** полный каталог, включая пустые папки; `h/l` сворачивают,
  раскрывают и переходят к родителю/ребёнку.
- **Поиск:** плоские результаты с заголовком, путём и коротким контекстом.
  Fuzzy-поиск названий/путей дополняется существующим FTS5 по содержимому.
- **Смешанный:** найденные заметки и headings сгруппированы по предкам;
  collapsed-состояние обычного дерева не скрывает совпадения. Breadcrumb
  ограничивает поиск выбранной папкой, включая подпапки.

Один файл объединяется в один результат; разные heading-цели остаются отдельными.
Ранжирование: точное название, prefix, последовательность символов, FTS rank;
при равенстве — полный путь. Регистр нормализуется Unicode lowercase.
Пустой запрос показывает recent/open notes либо дерево, а не FTS MATCH пустоты.

Picker разделяет режимы ввода и навигации. В Query/Insert обычные буквы вводят
запрос; Ctrl-j/k выбирают результат. Esc переводит Query в Normal, где Vim
редактирует запрос; следующий Esc переводит в Navigation. В Navigation `j/k`
двигают выбор, `/` возвращает Query, Enter открывает, Esc закрывает picker.
Закрытие восстанавливает исходный фокус/курсор; запросы не меняют основной текст.

Bindings: `<Space>ff` дерево, `<Space>fs` поиск, `<Space>fm` смешанный,
`<Space>vv` vault, `<Space>pp` палитра команд. Vault picker показывает recent
vaults из GlobalConfig, позволяет ввести новый путь и вызвать создание vault.
Смена vault использует существующие правила завершения I/O и recovery dirty
буферов. Удалённые каталоги показывают ошибку, ввод нового пути допускается.

Работа поиска идёт через catalog worker: каждое сообщение несёт VaultEpoch,
QueryGeneration и идентификатор picker. При смене запроса/папки/режима/закрытии
picker поколение меняется. Принимается только точное текущее поколение.
Страницы — до 100 результатов; ввод объединяется debounce и ограниченной очередью.
Dirty-буферы дают overlay результатов и подавляют устаревшие дисковые совпадения.
В смешанном режиме дерево строится по результатам, а не сканируется из GUI.

### 2.1. Обязательные условия скорости поиска

Индекс сохраняется между запусками. Startup reconcile и файловые операции
обновляют только изменённые записи; стабильные file IDs не перенумеровываются.
Во время initial indexing каталог обслуживает интерактивные запросы между
порциями до 16 файлов. Нельзя ставить поиск за полным rebuild хранилища.

Нормализованные title/path/heading хранятся в памяти catalog worker и меняются
при обновлении конкретного документа. Запрос не читает заметки с диска,
не извлекает повторно MarkdownFacts и не сортирует все совпадения: выбирает
bounded top-k. Полнотекстовая ветка использует SQLite FTS5; из неё извлекаются
до 101 записи для страницы 100 с has_more, без обязательного COUNT всех matches.
Dirty-текст передаётся снимком Rope при изменении revision; рабочий search overlay
своевременно исключает дисковую версию и не переписывает канонический индекс.

Ввод debounce 35 ms. Очередь поиска хранит только последний ожидающий запрос;
промежуточный запрос отменяется при следующем поколении. Это не отменяет durable
файловые jobs. UI выполняет только ввод, отправку запроса и отрисовку страницы.

Предлагаемые измеримые бюджеты для release на текущем компьютере, 10k файлов
по 4 KiB, русский/английский текст, прогретый индекс: p95 выдачи первых 100
результатов по title/path/heading ≤50 ms, полной смешанной выдачи с FTS ≤150 ms.
Граница — последний ввод → применение результата, включая debounce/worker queue;
отрисовка измеряется отдельно. Во время индексации целевой p95 ≤250 ms.
Один чрезмерно большой файл может превысить порционный бюджет; worst-case
измеряется отдельно и не скрывается усреднением. Бюджеты подтверждаются
замерами, а не объявляются выполненными по архитектуре. Для 100k файлов
фиксируются latency и память как отдельный stress-case.

## 3. Быстрые ссылки

`gf` следует ссылке под курсором. `<Space>jl` включает Flash только по ссылкам
видимой области: метка сразу открывает выбранную цель. Обычный `s` остаётся
Flash по словам. `<Space>ll` открывает picker всех ссылок активной заметки.
Локальные headings и block anchors используют тот же resolver.

Цели берутся из текущих MarkdownFacts с BufferId/Revision; устаревшая карта
не применяется. Visible ranges ограничивают отрисовку и число меток. Повторные
вхождения остаются отдельными; ссылки внутри code не становятся целями.
Неоднозначное имя открывает picker кандидатов; отсутствующая заметка предлагает
создание через обычную команду. HTTPS/HTTP/mailto идут через платформенное
открытие; неподдерживаемые схемы показывают ошибку.
Ctrl-o/Ctrl-i перемещаются по общей истории note+anchor переходов.

## 4. Папки, оглавления и раскрытие идей

Picker и sidebar показывают настоящие каталоги, включая пустые. Создание,
rename, move и trash действуют на выбранный файл/папку. Rename папки обновляет
пути её открытых буферов и внутренние ссылки на потомков. Dirty-файлы внутри
поддерева или среди переписываемых ссылок блокируют операцию с понятным сообщением.
Все операции выполняются через расширенный FileOpPlan с staging/recovery.

`<Space>oo` — outline активного файла; `<Space>of` — outline папки.
Иерархия папка → заметка → headings. `l` раскрывает заголовок с дочерними headings
и excerpt секции; Enter открывает исходный файл на соответствующей позиции.
Свернутые секции не загружают свои тексты. Идея представлена Markdown-секцией
под heading; отдельной дублирующей базы «идей» нет.

`<Space>oi` создаёт `_index.md` в выбранной папке или обновляет управляемый блок
между `<!-- truff:toc:start -->` и `<!-- truff:toc:end -->`. Вне блока любой
пользовательский текст сохраняется. Первый запуск включает автообновление этой
папки; после изменения файлов/heading блок пересчитывается в фоне и применяется
через обычный Buffer/save с проверкой fingerprint. Несохранённый `_index.md`
не перезаписывается: показывается предложение обновить блок одной undo-транзакцией.
Файл `_index.md`, `.truff` и генерируемый блок исключаются из собственной выдачи.
Отсутствующие/повторные маркеры требуют явного исправления, текст не угадывается.

## 5. Таблицы по типу Dataview

Read-only представления объявляются fenced-блоком `truff-query`:

````markdown
```truff-query
from = "projects"
view = "table"
columns = ["title", "path", "tags", "modified"]
tag = "research"
sort = "modified:desc"
limit = 100
```
````

Синтаксис использует уже имеющийся TOML. `from` — относительная папка (включая
потомков), `view` — table/list, фильтры — title substring и точный tag.
Поля: title, path, headings_count, tags, created, modified; дополнительные
метаданные — строковые значения из fenced `truff-meta` TOML-блока в начале файла.
created отсутствует для старых файлов без метаданных; modified берётся из stat.
Tags задаются массивом в truff-meta, не извлекаются эвристикой из обычного текста.
Неизвестное поле/оператор — ошибка у блока. limit ограничен 1..1000,
результаты приходят страницами по 100. SQL формируется из типизированного плана
с allowlist колонок и bound parameters; произвольного SQL/JS нет.

`MarkdownFacts` единожды извлекает query/meta-факты; store индексирует метаданные.
Dirty overlay применяется до сортировки/пагинации, чтобы не показывать дубликаты
или устаревшие строки. GUI рисует виртуальные строки, Enter открывает заметку,
motions выбирают строку/ячейку. Генерируемая таблица не вставляется в исходник;
в Source виден запрос, в Preview — результат или локальная ошибка.

## 6. Лента отдельных заметок

`<Space>ns` открывает ленту vault или выбранной папки. Одна полоса чтения:
карточки с заголовком, временем, путём и раскрываемым Markdown-содержимым.
Есть два порядка: новые записи и давно не открывавшиеся. По умолчанию — новые;
переключение доступно клавишей и в заголовке. Непросмотренные старые заметки
в режиме возвращения идут первыми; last_opened — производная локальная
статистика в SQLite, не изменение исходного Markdown.

`j/k`, counts, `gg/G`, Ctrl-d/u выбирают записи, Enter раскрывает/сворачивает.
`e` открывает выбранную запись в существующем редакторе в той же центральной
области; Esc из Normal возвращает к прежней позиции ленты. Текстовые motions
работают через тот же Buffer/View, включая undo/save/recovery.
Поиск и фильтр папки используют общий picker.

`<Space>nn` создаёт запись в текущей папке ленты, входит в Insert и показывает
пустой черновик. Имя `<UTC-timestamp>-<collision-suffix>.md` выбирается через
create-new без перезаписи. Первая save фиксирует Markdown с truff-meta.created;
черновик до сохранения доступен recovery. Следующая новая запись не уничтожает
предыдущий черновик. Время/суффикс не служат заголовком: название берётся из H1.
Лента обновляется после подтверждённого save. Пустая несохранённая запись
закрывается без создания пустого файла.

Страницы содержат до 100 заголовков; тексты подгружаются для раскрытых записей
возле viewport, кеш ограничен 8 MiB. Dirty-буферы не выселяются из Workspace
и подчиняются его лимитам; кеш чтения не создаёт копии всех открытых буферов.
Чтение карточки и outline-секции не создаёт постоянную вкладку.

## 7. Kanban на Markdown

`<Space>kk` открывает board view активного файла. `<Space>kn` создаёт доску
через обычный диалог файла. Формат явно включает представление:

```markdown
<!-- truff:kanban -->
# Проект
## Backlog
- [ ] Изучить тему [[research]]
## Doing
- [ ] Собрать прототип
## Done
- [x] Создать хранилище
```

H2 определяет колонку; непосредственный task-list item под ней — карточку.
Вложенный список и продолжения входят в исходный диапазон карточки.
Другие блоки остаются обычным Markdown, их нельзя потерять при движении карточек.
Вложенные tasks не становятся отдельными карточками. Границы извлекаются общим
семантическим parser с byte ranges, а не разбором отображаемого текста.

`h/l` выбирают колонку, `j/k` карточку, counts и `gg/G` работают в колонке;
`H/L` переносят карточку в соседнюю колонку, `J/K` меняют порядок;
`o` создаёт карточку, `e` редактирует её через Vim-поле/редактор,
`x` переключает checkbox, `dd` удаляет карточку, `u`/Ctrl-r undo/redo.
Enter открывает текст карточки; `<Space>jl` даёт её link hints.
Изменения checkbox явные: перенос в колонку с произвольным названием сам
не меняет статус. Заголовки колонок можно редактировать и переставлять командой
picker; удалить колонку с карточками можно только после выбора назначения.

Каждая правка строит одну Transaction против BufferId/Revision.
Move переносит исходный диапазон без сериализации остального файла, сохраняет
line endings, markup и ссылки. Смена Source/Preview/Board не меняет текст.
При внешнем изменении действуют обычные правила Conflict и Save.
Большая доска виртуализирует колонки и карточки; тексты не копируются на каждый frame.

## Владельцы и границы интеграции

| Ответственность | Владелец и точки интеграции |
| --- | --- |
| Command IDs, contexts, defaults, подсказки | `core/commands/`, `core/config/`; без отдельного списка UI bindings |
| Parser, motions, операторы любых текстов | `core/vim/`, `core/text/`; новый field adapter только связывает существующие типы |
| Строки, выбор, ancestor visibility | `core/navigation/`; `ui/shell/` маршрутизирует typed target |
| Headings, links, metadata, query, board source ranges | `core/markdown/`; focused submodules, один extractor |
| Типизированный query plan и kanban Transactions | предметные модули core; egui не определяет правила |
| Каталог, пустые папки, поиск, лента, метаданные | `store/catalog/`, `store/index/`; existing bounded worker и SQLite |
| Folder operations, generated index save | `store/operations/`, `store/files.rs`; существующая recovery/conflict модель |
| Picker state, feed state, board state | focused modules `ui/app/`; Application только координирует |
| Визуализация picker/outline/feed/board/fields | focused modules `ui/native/`; одна Theme и виртуализация строк |
| Link hints и source-to-screen отображение | `ui/shell/flash.rs`, `ui/overlays/flash.rs`, editor DisplayMap |

Корни модулей только компонуют API. Новые feature-sized области не помещаются
целиком в `app/mod.rs`, `shell/routing.rs` или `native/events.rs`.
Новым сообщениям фоновых jobs обязательны epoch/generation, snapshot key при
использовании текста и ограничение payload. Late Follow и Backlinks также
проверяются: текущий CatalogEvent не гарантирует эти поля.

## Критерии приёмки

1. Только клавиатурой: выбрать vault → создать папку → создать запись →
   отредактировать через Vim → сохранить → найти в mixed picker → перейти по
   ссылке с буквенной меткой → вернуться → увидеть запись в ленте.
2. Табличная проверка всей матрицы Vim для редактора и коротких полей; IME,
   paste, кириллица, emoji, CRLF, operator counts и один undo-group.
   `?` не перехватывается справкой; default и remapped bindings дают те же действия.
3. Backlinks, TOC, дерево и picker используют один выбор; недоступный фокус,
   пустые результаты, Esc и повторный вход не меняют чужой текст.
4. Поиск видит совпадение в collapsed-папке; режимы сохраняют запрос и selection;
   dirty overlay верен, stale result после запроса/смены vault не принимается.
5. Пустая папка видна. Rename/move/trash поддерева сохраняют ссылки, блокируют
   dirty-conflict и проходят crash-recovery проверки FileOpPlan.
6. Автоиндекс не теряет текст вне маркеров и не перезаписывает внешнюю/dirty
   версию; обновление блока можно отменить. Повторные headings и циклические
   ссылки не вызывают рекурсивного разворачивания.
7. Query в Source/Preview, неверный запрос, теги, фильтр подпапки, pagination,
   missing metadata и dirty update проверяются на фиксированном vault.
8. Новая запись создаёт отдельный файл; возвращение к старым заметкам работает;
   crash до save восстанавливает черновик. Быстрый повтор create не перезаписывает файл.
9. Kanban create/edit/move/reorder/toggle/delete/undo/save/restart проверяются
   на Markdown с вложенными tasks, обычными блоками, links и CRLF.
10. GUI smoke отправляет клавиши реальному окну и проверяет сохранённые файлы,
    focus и визуальные результаты. Headless-тесты не объявляются GUI-проверкой.

Проверки после реализации:

```bash
rtk cargo fmt --all -- --check
rtk cargo check --offline --locked --workspace --all-targets
rtk cargo test --offline --locked --workspace
rtk cargo clippy --offline --locked --workspace --all-targets --all-features -- -D warnings
```

Для hot paths измеряются baseline и новая версия на одинаковых corpus:
10k файлов с вложенными/пустыми папками, 10 MiB заметка, 2k карточек.
Замеряются whole-process RSS/PSS, p50/p95 key-to-frame и query-to-result,
объём прочитанных данных и число видимых объектов. Повторное движение selection
не должно пересчитывать MarkdownFacts, читать файлы или сортировать весь vault.
Числовые результаты фиксируются после измерения, улучшение заранее не обещается.

## Последовательность интеграции

Единая маршрутизация и поля → picker/search/vault/link hints → папки/outline/
autoindex → metadata/query tables → лента → kanban → workspace/GUI/perf проверки.
Каждый шаг сохраняет пригодность текущего редактора. Все перечисленные функции
входят в запрос; эта последовательность не исключает последние пункты.
Детальный план с файлами и командами проверки составляется после review проекта.
